### LLM Library Architecture Overview

## 1. Call Semantics and Heterogeneity

The library distinguishes call semantics from provider heterogeneity. These two dimensions are orthogonal and must
not be coupled in the implementation.

# Call Semantics (Execution Patterns)

Call semantics describe how a set of LLM invocations is coordinated and completed:
- Single call — one invocation, completion is per request
- Independent concurrent calls — multiple calls, each completes independently
- Grouped / barrier calls — a set of calls that complete as a group (e.g. gather)
- First-success / race — completion occurs when one call succeeds
- Streaming calls — partial results are produced incrementally
- Detached calls — execution continues independently of the caller

Call semantics define completion behavior and cancellation propagation, not transport or provider behavior.

# Heterogeneity

Heterogeneity describes what is being called:
- Same provider, same model
- Same provider, different models
- Same provider, different credentials
- Different providers
- Mixed streaming and non-streaming calls

The library explicitly supports heterogeneous groups. No call semantic assumes homogeneity of provider, model,
credentials, or transport characteristics.

Invariant:
- Call semantics must operate identically regardless of provider heterogeneity.

## 2. Separation of Concerns

The library is structured around three strictly separated layers:

# 2.1 Call Coordination Layer

Responsible for:
- Logical operations
- Grouping and barrier semantics
- Completion signaling
- Cancellation propagation

This layer:
- Is provider-agnostic
- Is transport-agnostic
- Does not perform scheduling or rate limiting

It models intent, not execution.

# 2.2 Policy & Admission Layer

Responsible for:
- Rate limiting
- Concurrency limits
- Retry and jitter policies
- Endpoint and credential scoping
- Transport engine (CURLM) selection

This layer:
- Is provider-aware only via metadata
- Enforces constraints before requests enter transport
- Does not understand call semantics beyond admission needs

# 2.3 Transport Layer

Responsible for:
- HTTP execution
- Connection management
- Protocol correctness
- Backpressure propagation

This layer is implemented using libcurl (CURLM) and is intentionally opaque to users.

## 3. The LLMClient Boundary
# 3.1 Definition

An LLMClient represents a fixed execution context for a class of LLM requests.

An LLMClient encapsulates all properties that must remain stable to ensure correct transport behavior,
policy enforcement, and connection reuse.

An LLMClient defines:
- Provider (e.g. OpenAI, Anthropic, Gemini, local)
- Authentication material (API keys, tokens, credentials)
- Base endpoint / host
- Model family or compatibility mode
- Provider-specific protocol decisions (headers, streaming mode, request shape)

Once created, an LLMClient is treated as immutable.

# 3.2 What an LLMClient Is Not

An LLMClient is not:
- A scheduler
- A queue
- A thread
- A transport engine
- A rate limiter
- A workflow executor

Those responsibilities live in policy and transport layers.

# 3.3 Why LLMClient Is a First-Class Concept

The LLMClient boundary provides:
- A natural unit for connection reuse
- A stable key for rate limiting and admission control
- Clear isolation between providers and credentials
- A clean seam for cross-provider normalization

Invariant:
- Requests are submitted through an LLMClient, not directly to the system.

This prevents accidental cross-provider batching and ambiguous policy behavior.

## 4. Explicit Provider APIs vs Normalized APIs

The library intentionally supports two API surfaces:

# 4.1 Explicit Provider APIs

These APIs:
- Map directly to provider-specific features
- Preserve full access to provider capabilities
- Reflect provider-native request/response models

Examples include:
- OpenAI chat/completions
- Anthropic messages
- Gemini multimodal APIs

These APIs are explicit by design and are not forced into a common abstraction.

# 4.2 Normalized API

In addition, the library provides a minimal normalized API intended for common cross-provider usage.

The normalized API:
- Operates after LLMClient selection
- Defines a minimal shared request/response model
- Enables portable usage across providers
- Does not constrain transport or policy layers

Normalization is an opt-in convenience, not a replacement for provider APIs.

## 5. Interaction Between Layers

Putting the pieces together:
- A user selects or creates an LLMClient
- A logical operation is defined (single, grouped, streaming, etc.)
- The operation is admitted through policy
- Provider-specific requests are generated by the client
- Requests enter the transport layer
- Completion is signaled according to call semantics

At no point are:
- Transport details exposed to the user
- Provider assumptions leaked into call semantics
- Scheduling logic embedded in provider clients

## 6. Design Intent Summary
- Call semantics and heterogeneity are orthogonal
- LLMClient defines a fixed provider execution context
- Provider-specific APIs remain first-class
- Normalization is layered, not forced
- Transport remains opaque and policy-driven
- The architecture supports future orchestration without embedding it
